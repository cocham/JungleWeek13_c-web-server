# 팀 작업 공통 양식

[목차](README.md) · [브랜치와 PR 운영 절차](02-pull-requests.md)

아래는 이슈 #5의 작업을 예로 들어 이슈 → 브랜치 → 커밋 → PR을 연결한 양식이다. 대괄호와 예시 번호는 실제 작업에 맞게 바꾼다.

## 1. 이슈

**제목** `[HTTP] 분할 수신된 POST 본문 처리`

```markdown
## 구현 목표
Content-Length가 있는 POST 요청의 본문을 선언된 길이까지 읽어 라우터에 전달한다.

## 요청 처리 흐름
소켓 읽기 → HTTP 본문 처리 → 라우터 → /api/echo

## 학습 질문
본문을 읽는 도중 연결이 끊기면 누가 버퍼를 해제하는가?

## 테스트 / 완료 조건
- [ ] 본문을 한 번에 보낼 때와 나눠 보낼 때 /api/echo 응답이 동일하다.
- [ ] 본문이 다 오기 전에 연결이 끊기면 라우터를 호출하지 않는다.
```

현재 GitHub 양식에서 구현 목표, 요청 처리 흐름, 테스트 / 완료 조건은 필수다. 협업 이슈는 요청 처리 흐름 칸에 작업 순서나 선행 이슈를 적는다. 학습 질문은 필요할 때 추가한다. 공통 헤더나 함수 계약에 영향이 있으면 관련 담당자와 선행 이슈를 적는다. [저장소 이슈 양식](../../.github/ISSUE_TEMPLATE/feature-learning.yml)

## 2. 브랜치 이름

개별 작업은 `타입/이슈번호-짧은-영문-설명`으로 이름을 붙인다. 예시는 `fix/5-post-body`다. 공통 서버를 올리는 첫 브랜치는 `feat/baseline`을 사용한다. 팀원별 첫 분기와 이후 분기 기준은 운영 절차를 따른다. [브랜치 운영 절차](02-pull-requests.md)

## 3. 커밋 메시지

기본 형식은 `타입(영역): 변경 내용`이다. 영역은 `tcp`, `http`, `static`, `proxy`, `build`, `repo`처럼 소문자로 적는다. 변경 내용은 어떤 동작이 바뀌었는지 한국어 한 줄로 적는다. 한 커밋에는 함께 설명할 수 있는 변경을 담는다.

| 타입 | 사용 시점 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat(proxy): /api 요청을 백엔드에 전달` |
| `fix` | 동작 오류 수정 | `fix(http): 분할 수신된 POST 본문을 끝까지 읽기` |
| `refactor` | 동작을 유지하며 코드 구조 변경 | `refactor(tcp): 연결 종료 경로 정리` |
| `test` | 테스트 추가·수정 | `test(http): 분할 본문 수신 검증 추가` |
| `docs` | 문서 변경 | `docs(repo): 공통 실행 명령 정리` |
| `chore` | 빌드·저장소 설정 관리 | `chore(build): 테스트 빌드 대상 정리` |

## 4. PR

**제목** `fix(http): 분할 수신된 POST 본문을 끝까지 읽기`

```markdown
## 관련 이슈
Closes #5

## 변경 내용
- 바뀐 동작과 요청 흐름, 관련 파일·함수
- 공통 인터페이스 변경과 합의한 내용이 있으면 기록

## 검증
- 실행한 명령 → 실제 결과
- 버그 수정이면 실패 재현 방법과 수정 후 기대 결과
- 실행하지 못한 항목과 이유가 있으면 기록
```

이 PR로 이슈가 완료되면 `Closes #5`를 사용한다. 부분 작업이면 `Refs #5`로 연결한다. squash merge 때 PR 제목을 기준으로 최종 커밋 제목을 정리한다. [#23 PR 협업 규칙](https://github.com/cocham/JungleWeek13_c-web-server/issues/23)
